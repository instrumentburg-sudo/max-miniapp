## Каталог

Источник — действующие таблицы ocStore на RU-хосте, корень категории 164. Отдельного каталога товаров нет. Как в B0, JSON кэшируется на 600 секунд, фото берётся из общего `image/cache` в размере 400×400. Название удаляет только точное совпадение артикула и пробела в начале: `012E Лобзик Makita` → `Лобзик Makita`; сам артикул сохраняется отдельным полем. Внутренние коды из середины имени не удаляются.

Контракт `GET /max-api/catalog`:

```text
{builtAt, catalogVersion:2,
 categories:[{id,name,count}],
 items:[{id,article,name,categoryId,category,pricePerDay,available,image,url,deposit}]}
```

Поля B0 сохранены. `deposit` добавлен из `product_description.description`: только явное `Залог: N` даёт число. `Залог: 0 ₽` даёт 0; отсутствие суммы даёт `null`, а не обещание отсутствия залога. Предшествующая фраза `Залог возвращается` не скрывает последующую сумму. Сам B0 поля залога не имел: прежняя форма обещала уточнение менеджером.

Это информационный залог из той же карточки ocStore. Стоимость бронирования и его условия по-прежнему определяет серверный intake quote; PHP не создаёт Z и не подменяет quote. Если источники расходятся, интерфейс должен показывать, что залог уточняется, а не выдавать неизвестный 0 за «без залога». Старая версия кэша пересобирается; при сбое БД допускается прежний кэш с `deposit:null` у позиций без этого поля.

На zayavka разрешается только точный read-only GET-прокси `/max-api/catalog`. Открывать общий PHP namespace ради каталога не требуется.

## Локальные проверки

```bash
php -l api-php/index.php
php tests/catalog.php
php tests/webhook.php
```

`catalog.php` проверяет проекцию карточки, название, фото, категории, неизвестную/нулевую/числовую сумму залога и реальные ранние 410 обеих старых форм. `webhook.php` проверяет единственного ответчика, forwarding без fallback и сохранённый B0 запрет групп/каналов. Проверки не загружают production env и не отправляют HTTP-запросы.
